01

Executive summary

JARVIS is a well-factored local-first assistant — 16 agents, typed settings, a real eval harness, 102 test files with serious mutation-testing discipline — but every architectural assumption bakes in “one human, watching, in a terminal, on localhost.”

The web GUI has no authentication and accepts WebSocket connections from any origin (chat_ws.py:22), which is tolerable today and becomes full remote takeover the moment JARVIS is exposed beyond the machine. The agent already assembles all three legs of the “lethal trifecta” — private vault data, untrusted web content, and write/exec tools8 — so unattended runs must be designed by removing a leg per job, not by trusting guardrails; even production classifiers miss ~17% of dangerous actions10.

Autonomy is further blocked by a single global session, confirmation handlers that deadlock or silently reject without a human, and no spend limit beyond a 5-iteration cap (stream_handler.py:31). The feedback-loop story is weakest where it matters: golden evals bypass the real StreamHandler, so the exact loop changes you plan would be invisible to them. On access, Telegram long polling is the standout — outbound-only, works behind NAT, no exposed ports13 — paired with Tailscale for the GUI. On hosting, the Things 3 dependency plus local-first preference make a headless Mac mini running JARVIS as a LaunchAgent the clear recommendation. The roadmap puts safety rails and the session refactor first, one read-only scheduled loop plus Telegram second, eval hardening third, deeper autonomy last. Phase 1 is startable this week and is mostly small, boring changes — which is exactly the point.

Revision 2026-08-19. A strategic-positioning pass (now ADR-034 in the repo) was folded into this dossier: with coding-agent harnesses (Claude Code, Codex, OpenCode) now commodities, JARVIS is explicitly the personal context, memory, and workflow hub — it delegates coding execution to external harnesses instead of growing its own (DEV-02/03 rescoped), and exports its context to every tool via a new Cortex-backed MCP server (initiative HUB). See the new Strategic position section; the in-repo roadmap.md (initiatives AON, HUB, DEV) is the authoritative, evolving version of section 07.

02

Codebase audit

A · Security assumes a watching human on localhost

Critical

The single most important theme: nearly every safety property depends on a human being present at a local terminal. That holds today and collapses the instant JARVIS is tunneled or scheduled.

  • CritNo auth, no WebSocket origin checkchat_ws.py:22 accepts unconditionally; CORS (app.py:67-73) doesn’t gate WebSockets — any website you visit can drive the agent via your browser today.
  • CritPrompt-injection → RCE chainWeb content enters context verbatim (web_fetch.py, web_search.py); test_tools.py:29-42 runs pytest (arbitrary Python via conftest) with no confirmation; the developer agent bundles write+git+test tools.
  • HighFilesystemGuard is bypassed by most write toolsOnly obsidian/vault.py and outcome_tools.py consult it; codebase_tools.py, project_write_tools.py, git_tools.py roll their own access logic.
  • HighUnauthed settings API can persist a malicious MCP serverroutes/settings.py → mcp/client.py; MCP tool descriptions are injected into the prompt unvetted (mcp/bridge.py).
  • HighThe GUI server is the biggest test blind spot~143 never-executed mutants across app.py, state.py, chat_ws.py — the exact code you’d need to secure has no safety net.

B · Human-in-the-loop gates & single-session design block autonomy

High

Confirmation deadlock: confirmation.py:98 waits on a threading Event with no timeout, and chat_ws.py:65 awaits the turn inside the same receive loop that handles approvals — a vault-write approval wedges the session. Headless CLI silently rejects on EOF.

One global session: app.py:36 builds a single GuiSession with takeover semantics; turns are serialized. Background jobs, Telegram, and chat cannot coexist. No spend circuit breaker: only the 5-iteration cap; per-response cost_usd is computed but never enforced.

C · Duplicated orchestration, non-reentrant core

High

Per-turn orchestration is hand-duplicated between apps/cli/main.py:705-809 and apps/gui/server/bridge.py:41-260, already diverging. StreamHandler keeps per-call state on self, permanently mutates max_tokens, and duplicates the agentic loop (~120 lines, twice). Every loop-engineering change currently lands in 2–4 places — and a Telegram front end would be copy number three.

E · Host portability & F · Evals don’t guard the code that matters

High

Portability: all 21 skills are gitignored absolute-path symlinks to a private sibling repo with soft-fail resolution — a fresh clone runs silently degraded. Things 3 is doubly macOS-GUI-bound. Evals: golden tests reimplement the loop and hardcode the prompt (test_golden_conversations.py:319-400), bypassing the real StreamHandler — exactly the code the roadmap changes — and the judge silently fabricates 0.5–0.6 fallback scores. Reliability · Med Non-atomic JSON saves lose a conversation on mid-turn crash; MCP never reconnects; context is frozen at startup.

03

Loop engineering

You asked about “loop engineering” in three senses. Each maps to different JARVIS subsystems, token math, and security posture.

3a · Autonomous agentic loops

Today the loop lives in stream_handler.py (duplicated), capped at 5 iterations, with all state in-process. Anthropic’s harness research is unambiguous that the path past a small cap is external state, not a bigger number: a JSON task list with per-item pass/fail, a progress-notes file, and git checkpoints1. Concretely: deduplicate the loop into a shared TurnRunner in packages/core; add tool-result clearing — “one of the safest lightest-touch forms of compaction”2; and extend delegation past its one-hop ceiling only after sub-agents return distilled 1–2k-token summaries.

Tokens

Each iteration re-sends the whole context; with a ~12KB skill prompt inlined every turn, iterations 6–15 can cost 3–5× iterations 1–5. Counters: tool-result clearing, and prompt caching — a 500-session study found caching cuts cost ~45–80% if static content sits in a stable cached prefix5. JARVIS’s per-turn skill inlining is currently cache-hostile.

Security

Longer loops mean more consecutive un-reviewed tool calls, compounding the Theme-A injection chain per iteration. The unconfirmed pytest runner is the single worst offender.

Evals

Any loop change is invisible to the golden suite because it reimplements the loop. Rewiring evals through the real TurnRunner is a precondition for touching iteration logic safely.

3b · Scheduled / background runs

First principles A daemon runs without a terminal attached, started by the OS. On macOS the scheduler is launchd: you drop a small plist describing “run this at this interval,” and it handles starting, restarting, and logging — macOS’s cron, but supervising too. A LaunchAgent runs inside your logged-in GUI session (and can talk to Things 3); a LaunchDaemon runs outside it and cannot18. That one fact shapes the hosting decision.

There’s zero scheduling code today, and that’s fine — the scheduler should stay outside the app (launchd invoking a CLI entry point). What must change inside: a headless entry point (jarvis run-job); a PolicyConfirmationHandler that auto-approves a whitelist and routes everything else to a persisted approval inbox; a persisted cost ledger with a daily budget abort — the Agent SDK ships max_budget_usd3, OWASP suggests a $10/session cap11; and per-turn context refresh (tasks.md is synced once at startup).

Security

Every scheduled job must drop one leg of the lethal trifecta8, because no guardrail is reliable enough to substitute (17% false-negatives10). Safest first job: a read-only briefing (vault + Things → message) — drops external writes. Never schedule the developer agent unattended — since ADR-034 this is structural: JARVIS never executes coding runs itself (see §06).

Tokens

A daily briefing is cheap and predictable — ~$0.05–0.20/day — and an ideal caching candidate (identical prefix daily), but only bounded once the budget check exists.

Evals

Scheduled jobs produce artifacts gradeable with deterministic code checks (“does the briefing mention every task due today?”), which Anthropic recommends over LLM judges6. Each job ships with its output check.

3c · Feedback / improvement loops

The raw materials exist and are disconnected: golden evals, outcome tracking (outcome_tools.py), a manual review CLI (review.py), telemetry, and ChromaDB RAG. Fixes in value order: (1) make evals test the real system and fail loudly instead of fabricating 0.5–0.6 scores; (2) turn on regression gating — read the baseline result_storage.py already writes; at ~$0.41/run even every-PR is noise-level7; (3) calibrate the judge once against ~25 hand-labeled transcripts, since consistency ≠ correctness12; (4) automate the outcome loop as a weekly read-only job, the natural home for typed memory — Mem0-style fact extraction beats raw-transcript RAG (>90% token savings), and graph memory adds only ~2%, so skip it17.

Anti-over-engineering verdict Extract facts to Markdown/JSON in the vault; don’t adopt a memory framework. The whole feedback layer costs less per month than one runaway agentic turn — which is the argument for building it before autonomy, not after.
04

Always-on access

Channels

Messaging — Telegram, clearly. Long polling means the bot makes outbound requests to Telegram and holds the connection open — no inbound port, no public HTTPS, works behind any home NAT13. Signal via signal-cli needs a JRE, a constant receive loop, and updates every ~3 months or it breaks14 — a treadmill with no payoff for one user. A Telegram bot is just a third front end, which is why the shared TurnRunner extraction is its real prerequisite.

Web app — Tailscale. Tailscale builds an encrypted private network among your own devices; Serve exposes a local port only inside it — your phone reaches the GUI, the internet cannot15. Given the GUI has no auth, tailnet-only is the only responsible exposure. Non-negotiable regardless: fix WebSocket origin checking and add token auth first — “private network” should be the second wall, not the only one.

Voice — later, but proven viable. Home Assistant Assist ships a “Hey Jarvis” wake word with ~$13 ESP32 satellite hardware20. Fun, but it depends on everything above. Park it.

Recommendation

A headless Mac running JARVIS as a LaunchAgent, reached via Tailscale. Things 3 has no server API — Cultured Code’s own docs say “if it’s not documented, it’s not possible”19 — so any non-Mac host silently amputates a live integration, and the codebase is macOS-coupled elsewhere too.

It must be a LaunchAgent with auto-login, not a LaunchDaemon, because only an agent in a logged-in GUI session can send Apple Events to Things18. Headless recipe: FileVault off (its pre-boot lock blocks remote access after a reboot), auto-login, auto-restart after power loss, pmset -a sleep 0 — sleep is the main availability failure on Apple Silicon minis21. Disabling disk encryption is acceptable only because access stays Tailscale-scoped. Revisit a VPS only if Things is ever dropped.

05

Unknown unknowns

Capabilities the field treats as table stakes that JARVIS doesn’t yet have — filtered for a one-person, local-first assistant.

Worth adopting

  • Tool descriptions are the cheapest lever anywhere. Rewriting them alone cut task time 40% in Anthropic’s tests22. An afternoon on packages/core/tools/* may outperform any architecture work here.
  • Typed memory extraction over raw-transcript RAG — the ChromaDB approach is one generation behind fact extraction (>90% token cut)17.
  • Tiered trust for sessions — run scheduled jobs with reduced tool groups; JARVIS’s per-agent tool binding already supports this structurally23.
  • Khoj as existence proof — the closest comparable (self-hosted, Obsidian-centric) ships scheduled automations and thin multi-device clients24. Proactivity is table stakes, not exotic.

Consciously skip

  • Parallel multi-agent fan-out — ~90% eval gains but ~15× token cost22. Wrong trade for one person.
  • Graph memory — ~2% gain over typed extraction17.
  • LangGraph-style frameworks — but steal the insight: durability lives in a pluggable SQLite checkpointer; in-memory state loses everything on restart25 — exactly JARVIS’s current failure mode.
06

Strategic position (added 2026-08-19, ADR-034)

The tool landscape question: with Claude Code, Claude Cowork, OpenAI Codex, OpenCode, and Pi in daily reach, where does JARVIS fit — and what has it built that already exists? The tools all run agentic loops, but they sit at different layers:

ToolLayerCompetes on
Claude Code / Codex / OpenCodeCoding agent harnessLoop quality: sandboxing, planning, headless/CI modes, subagents
Claude CoworkGeneral knowledge-work harnessNon-coding agentic work over docs, files, connected tools
PiMinimal open harnessSimplicity; same loop, deliberately tiny
JARVISPersonal context & workflow hubYour vault, context files, memory, voice, integrations, provider independence
Positioning verdict

Harnesses are commodities; the context is the moat. Nothing in the harness column is worth competing with as a solo project — and nothing in JARVIS’s row is provided by any harness. Build the moat, rent the harnesses, connect them with MCP.

What this changes

DEV-02/03 rescoped: delegate, don’t rebuild. The developer agent’s DEV-01 tool set was a hand-rolled miniature Claude Code, and its planned follow-ons (AutoConfirmationHandler, planning phase, heartbeat execution, PR creation) re-created what Claude Code ships as headless mode (claude -p), the Agent SDK, permission policies, and scheduled agents. /develop becomes a thin dispatcher: JARVIS decides what to improve and composes the context; the external harness executes and opens PRs. The DEV-01 tools survive only as a fast path for tiny scoped edits (meta.yaml, prompts).

New initiative HUB: export the context via MCP. Cortex (ADR-029) already anticipated this (“MCP-ready”). HUB-01 wraps its semantic search as a local, stdio-only MCP server registered in Claude Code and consumed by JARVIS itself; HUB-02 adds context files and typed memory (post-quarantine facts only, per AON-03). Every harness is an MCP client, so this ends copy-pasting context between tools — and flips JARVIS’s most valuable asset from “locked inside JARVIS” into the shared memory backbone of the whole toolchain. The single-source-of-truth pattern already works here: CLAUDE.md pointing at AGENTS.md, skills as symlinks — MCP generalizes it to live data.

AON scope guard. The TurnRunner, front ends, and read-only scheduled jobs stay — they serve JARVIS’s own conversational loop, which no harness replaces. But harness-grade depth beyond that (unattended code-editing sandboxes, long autonomous coding loops) is out: delegated. The audit’s “never schedule the developer agent unattended” is thereby structural, not just policy.

Unchanged, deliberately: workflow agents (writer, reading assistant, publisher…), voice profile, provider routing, token economics, Obsidian/Readwise/Things 3/Substack integrations, and the GUI. None of the listed tools do any of it.

Phased roadmap

2026-08-19 note These phases now live in the repo as milestones AON-01…05 (plus the 2026-07-31 delta-review amendments) — docs/product/roadmap.md is authoritative. The ADR-034 revision adds initiative HUB (Cortex as MCP server; independent of AON sequencing, startable any time after AON-01) and rescopes DEV-02/03 to delegated execution — the “deeper autonomy” in Phase 4 below concerns JARVIS’s own scheduled loops only, never self-executed coding runs.

Ordered by value-per-effort. Effort per step is S/M/L; each phase carries an overall effort, risk, and token-impact note.

1

Safety rails & the shared core

Make the existing system safe to leave running and cheap to extend. Start this week.

Effort MRisk Low
  • WebSocket origin allowlist + token auth in chat_ws.py/app.py; add TestClient coverage for the 143-mutant blind spot.S
  • Add a confirmation gate to the unconfirmed pytest runner (test_tools.py:29-42).S
  • Persisted SQLite cost ledger + daily budget abort in StreamHandler, per max_budget_usd3.S
  • Fix the confirmation deadlock: timeout on confirmation.py:98, move approval handling out of the blocked receive loop.M
  • Rewrite tool descriptions across packages/core/tools/*22.S
  • Atomic conversation saves (write-temp-then-rename) in memory.py.S

Token impact: neutral-to-negative — budget cap + better tool descriptions reduce waste.

2

Session refactor + first loop + Telegram

One core, many front ends, one safe scheduled job.

Effort LRisk Med
  • Extract TurnRunner + headless session factory into packages/core; de-duplicate StreamHandler’s twin loops. The one refactor everything rides on.L
  • Session-per-conversation replacing the global GuiSession.M
  • PolicyConfirmationHandler with whitelist + persisted approval inbox.M
  • jarvis run-job + launchd LaunchAgent; first job = read-only morning briefing8; refresh tasks.md per run.M
  • Telegram bot via long polling13 as a thin TurnRunner client; Tailscale Serve for the GUI15.M

Token impact: +$2–6/month for a daily briefing; bounded by the Phase-1 ledger.

3

Evals that guard the loop

Change loop code without flying blind.

Effort MRisk Low
  • Route golden evals through the real TurnRunner; remove the reimplemented loop and hardcoded prompt.M
  • Replace fabricated fallback scores with hard failures; read the baseline for CI regression gating7.S
  • Calibrate the judge against ~25 hand-labeled transcripts; randomize ordering12.S
  • Deterministic output checks for each scheduled job6.S
  • Automate the outcome-review loop as the second scheduled job, with typed fact extraction into the vault17.M

Token impact: ~$0.41/eval run + pennies for judges — negligible.

4

Headless Mac host + deeper autonomy

Dedicated always-on box; loops that run longer, safely.

Effort M–LRisk Med
  • Headless Mac mini: auto-login, FileVault off, pmset -a sleep 0, auto-restart, Tailscale-only21.M
  • Route FilesystemGuard through all write tools; add a quarantined web-digest job.M
  • Tool-result clearing2 + cache-friendly prompt assembly (static prefix first), targeting the 45–80% cut5.M
  • Raise the iteration cap only alongside file-based checkpoints (JSON task list + progress notes + git)1; MCP reconnection.M
  • Optional hardening: sandbox-runtime + credential-injecting egress proxy so the agent never holds API keys9.L

Token impact: net negative — caching + clearing should more than fund longer loops.
